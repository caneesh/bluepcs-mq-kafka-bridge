Runtime message flow#

Every transition emits an audit event; terminal outcomes are exactly three — completed, quarantined, discarded — and only those ack the MQ message. Details: BridgeOrchestrator AUDIT.md · event flow

The claim-check decision#

The enriched wrapper can exceed the broker's ~1 MB message limit, so Kafka carries a pointer: the wrapper lands in HDFS and the notification carries hdfsPath + checksum + eventId. During the Talend→bridge migration the product topic carries two formats; consumers discriminate by schemaVersion presence (present ⇒ claim-check, absent ⇒ legacy inline). Bump SCHEMA_VERSION on any breaking change — the resolver fails loudly on versions it doesn't know rather than guessing.

Delivery semantics & failure model#

End-to-end at-least-once: no XA across MQ/HDFS/Kafka — correctness comes from side-effect ordering plus idempotency (same eventId ⇒ same file name, same Kafka key), with downstream dedup. What each failure does:

FailureBehaviorCode
MQ broker outageJMS container reconnects forever (~5s interval); resumes where it left off MqConfiguration
Enrichment 5xx / timeoutClient retries with backoff; then failure → redeliver RestMarketingPlanApiClient
Enrichment 4xxNon-retryable → immediate failure → redeliver (poison guard bounds the loop) same
STS token failureTranslated to a retryable enrichment failure (never escapes unaudited) OAuth2JwtTokenProvider
HDFS write/verify failureTemp file cleaned, target never created → redeliver HdfsSafePayloadWriter
Kafka slow / broker failoverProducer's own budget governs (delivery.timeout 120s, max.block 60s); the publisher waits longer than both so its verdict is authoritative KafkaEnvelopePublisher · KafkaConfiguration
Unparseable payloadQuarantined to HDFS errors/, acked — permanent failures never loop BridgeOrchestrator
Poison messageOptional delivery-count guard discards with a full audit trail; MQ-side BOTHRESH preferred MqMessageListener
Null JMSMessageID / null bodyJMS-legal; eventId falls back to a payload hash, null body quarantines MqMessage
Crash between HDFS and KafkaNo ack → redelivery; HDFS write is skipped as already-existing, notify re-runs HdfsSafePayloadWriter
Timeout coherence rule: the publisher's synchronous wait must exceed max.block.ms + delivery.timeout.ms. A shorter wait reports failure for records still in flight — which then usually deliver anyway, guaranteeing duplicates and a false KAFKA_PUBLISH_FAILED audit.

Deployment topology#

The jar builds anywhere; only the fat jar, scripts, and a hand-created .env live on the edge node. Kerberos: HDFS via keytab login + scheduled relogin; Kafka via GSSAPI/JAAS; the STS is credential-header based, not Kerberos.
